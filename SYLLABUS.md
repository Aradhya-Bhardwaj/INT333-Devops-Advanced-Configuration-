## Unit I: Puppet Basics

- Configuration management systems: configuration management, pull and push
- Introduction to Puppet: why Puppet, components of Puppet
- Puppet architecture
  - Puppet Master: manifest, template, files, certificate authority
  - Puppet clients: agent, Facter
- Installation of Puppet
- Puppet development in isolation

This project uses Ansible (push model) for configuration management and has no Puppet code.

## Unit II: Advanced Puppet

- Puppet configuration and managing packages
- Puppet modules, classes and functions, including custom functions
- Monitoring web servers, load balancing clusters
- Scaling a Puppet environment, connecting agents to the master
- Dynamic configuration and extending Puppet
- Command line use, `puppet apply`, manifests

Not covered in this repository.

## Unit III: Nagios Monitoring

| Topic | Where |
| --- | --- |
| Continuous monitoring: definition, importance, benefits | A separate monitor server watches the application |
| Features, architecture, plugins | `check_http` and `check_tcp` in `ansible/roles/nagios/templates/dropwatch.cfg.j2` |
| Installation with a package manager (apt) | `ansible/roles/nagios/tasks/main.yml` |
| Setting up the web server | Apache with digest login, `ansible/roles/nagios/templates/nagios4-cgi.conf.j2` |
| Monitoring web servers | Homepage and login page checks |
| Built-in web interface: hosts and services | Nagios dashboard at `/nagios4` |
| Deploying a simple web application on a server | DropWatch, `ansible/roles/app/` |

Not covered: compiling Nagios from source. Soft and hard states, downtimes and comments are not configured in this code.

## Unit IV: Infrastructure as Code with Terraform

| Topic | Where |
| --- | --- |
| Architecture and workflow (`init`, `plan`, `apply`, `destroy`) | `DEPLOY.md` |
| Writing and managing configuration files | `terraform/main.tf`, `variables.tf`, `outputs.tf` |
| Provisioning on AWS | Two EC2 instances, two security groups, one key pair |
| Resources and dependencies | Instances reference the key pair and security groups; the inventory file depends on the instances |
| State | Local state file, excluded from Git |
| Terraform with Ansible | `local_file.ansible_inventory` writes the Ansible inventory |
| Best practices and security | SSH and Nagios limited to `admin_cidr`; secrets and state ignored by Git |

Not covered: modules, workspaces, remote state, Azure and GCP.

## Unit V: Introduction to Ansible

| Topic | Where |
| --- | --- |
| Ansible and configuration management, how it works | `ansible/site.yml` |
| Architecture: control node and managed hosts over SSH | `ansible/ansible.cfg` |
| From shell scripts to Ansible | Tasks in `ansible/roles/` replace manual setup commands |
| Installing Ansible | Prerequisites in `DEPLOY.md` |
| Inventory file | Generated by Terraform with `app` and `monitor` groups |

Not covered: Ansible with Vagrant.

## Unit VI: Advanced Ansible

| Topic | Where |
| --- | --- |
| Roles | `ansible/roles/app`, `ansible/roles/nagios` |
| Playbooks and `ansible-playbook` | `ansible/site.yml`, `DEPLOY.md` |
| Handlers | `handlers/main.yml` in both roles |
| Variables | `repo_url`, `app_dir`, and secrets passed with `-e` |
| Environment variables | `environment:` on the Django tasks, `dropwatch.env.j2` |
| Facts and built-in variables | Facts are gathered by default; templates use `inventory_hostname` and `groups` |
| Ansible with AWS for application deployment | DropWatch deployed to EC2 |

Not covered: prompts, tags, blocks.
